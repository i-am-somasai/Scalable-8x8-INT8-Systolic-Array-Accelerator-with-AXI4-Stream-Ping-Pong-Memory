# PROJECT CREATION RULES — MUST FOLLOW THROUGHOUT THE ENTIRE PROJECT

While creating the project, follow these engineering rules strictly. These rules have higher priority than convenience, brevity, or generating code quickly.

## 1. Build the project incrementally

Do **not** generate the entire RTL as disconnected modules.

Build and reason through the project in this order:

1. INT8 MAC Processing Element
2. PE testbench
3. 2×2 systolic array
4. 2×2 testbench
5. Parameterized systolic array
6. 4×4 configuration
7. 8×8 configuration
8. Array/controller interface
9. Input/output buffering
10. Ping-pong buffer controller
11. AXI4-Stream input
12. AXI4-Stream output
13. Main accelerator FSM
14. Top-level integration
15. Assertions
16. Complete verification environment
17. Python golden reference
18. Synthesis scripts
19. Timing constraints
20. Documentation

At every stage, check whether the newly created module is logically compatible with all previously created modules.

Do not proceed with an architectural assumption that has not been explicitly defined.

# 2. Establish the architecture BEFORE writing RTL

Before generating the RTL, explicitly define:

* Dataflow
* PE behavior
* Matrix dimensions
* K dimension
* Accumulation strategy
* Input/output data movement
* Number of cycles required for computation
* Pipeline stages
* Buffer organization
* AXI4-Stream packet structure
* `TLAST` semantics
* Matrix element ordering
* Buffer ownership
* Buffer switching conditions
* Reset behavior
* FSM states
* Counter behavior

Create a clear architecture specification first.

Do not write RTL until these decisions are internally consistent.

---

# 3. Do not hide ambiguity

If something is not defined, do not silently choose an arbitrary implementation.

For every important architectural decision, state:

**Decision → Reason → Consequence**

For example:

> Decision: Use output-stationary dataflow.
> Reason: Keeps partial sums local to each PE and reduces partial-sum movement.
> Consequence: A and B operands must be scheduled so that each PE receives the correct operands over successive cycles.

If multiple architectures are possible, select one and document why.

---

# 4. Keep the implementation genuinely scalable

The project is called:

**Scalable 8×8 INT8 Systolic Array Accelerator**

Therefore, scalability must exist in the RTL rather than only in the project description.

Use parameters such as:

```systemverilog
parameter int DATA_WIDTH = 8;
parameter int ACC_WIDTH  = 32;
parameter int ARRAY_ROWS = 8;
parameter int ARRAY_COLS = 8;
parameter int K_SIZE     = 8;
```

Avoid hard-coding:

```systemverilog
[7:0]
[31:0]
[7:0][7:0]
```

where parameters should be used.

The default configuration must be:

```text
ARRAY_ROWS = 8
ARRAY_COLS = 8
DATA_WIDTH = 8
ACC_WIDTH  = 32
```

Conceptually ensure the architecture can elaborate for:

```text
4×4
8×8
16×16
```

Do not claim that arbitrary matrix dimensions are supported unless the controller and tiling mechanism actually support them.

---

# 5. Be extremely careful with signed arithmetic

INT8 must be explicitly treated as **signed two's-complement**.

Define signedness clearly.

For example:

```systemverilog
logic signed [DATA_WIDTH-1:0] a;
logic signed [DATA_WIDTH-1:0] b;
logic signed [ACC_WIDTH-1:0] acc;
```

Do not depend on implicit SystemVerilog signedness rules.

Explicitly reason about:

```text
INT8 × INT8
     ↓
16-bit signed product
     ↓
32-bit signed accumulation
```

Check:

```text
+127 × +127
+127 × -128
-128 × +127
-128 × -128
0 × anything
```

Define the accumulator overflow policy.

Do not silently assume unlimited precision.

# 9. Clock and reset must be consistent

Use one clearly defined clock domain unless multiple domains are genuinely required.

Prefer:

```systemverilog
always_ff @(posedge clk)
```

with a clearly documented reset strategy.

If using synchronous active-high reset:

```text
rst = 1 → synchronous reset
rst = 0 → normal operation
```

Use the same reset convention across the design.

Check reset behavior for:

* PE
* systolic array
* buffers
* counters
* FSM
* AXI interfaces
* output registers

No stale state should survive reset.

# 10. Avoid accidental latches

For every `always_comb` block:

* assign all outputs on every path
* provide appropriate defaults
* ensure no incomplete assignments

For FSM logic:

```text
default assignments
↓
case(state)
↓
all relevant outputs assigned
```

Do not create unintended combinational storage.

---

# 11. Avoid multiple drivers

Every register or signal must have a clear owner.

Do not assign the same signal from:

* multiple `always_ff` blocks
* an `always_ff` and `assign`
* multiple combinational blocks

Before finalizing, perform a **multiple-driver audit**.

# 12. Systolic array must be cycle-accurate

Do not merely connect 64 MAC units in parallel and call it a systolic array.

The design must demonstrate actual systolic data movement.

Clearly define:

```text
A movement direction
B movement direction
Partial-sum location
PE-to-PE communication
Pipeline timing
Input skew
Output timing
```

For example:

```text
A → → → → 
B ↓ ↓ ↓ ↓
```

Document exactly which operand enters each PE on every cycle.

# 14. Clearly distinguish PE count from MAC operations

For the 8×8 array:

```text
8 × 8 = 64 PEs
```

If every PE performs one MAC per cycle during full utilization:

```text
64 MACs/cycle
```

is the theoretical peak.

Do not automatically claim:

```text
64 MACs/cycle sustained
```

because actual sustained throughput depends on:

* utilization
* memory supply
* controller behavior
* pipeline bubbles
* AXI backpressure
* matrix dimensions
* buffer switching

All performance numbers must be either mathematically derived or experimentally measured.

# 15. AXI4-Stream must follow handshake semantics

For every AXI4-Stream interface, correctly implement:

```text
TVALID
TREADY
TDATA
TLAST
```

A transfer occurs only when:

```text
TVALID && TREADY
```

When:

```text
TVALID = 1
TREADY = 0
```

the producer must hold the corresponding transfer information stable until accepted.

Explicitly verify this.

Do not lose data under backpressure.

# 16. Define TLAST precisely

Do not use `TLAST` arbitrarily.

Document:

> What exactly does one AXI packet represent?

Possible meanings include:

```text
one matrix tile
one matrix row
one output tile
one complete transaction
```

Select one architecture and use it consistently on both input and output paths.

The testbench must explicitly test `TLAST`.

# 18. Ping-pong buffering must be real

Do not simply create two memories and call them ping-pong buffers.

Clearly define:

```text
Buffer A
```


Ensure the loading side never overwrites data currently being consumed by the compute side.

# 23. Keep the PE simple and reusable

The PE should perform a well-defined operation such as:


Do not put:

* AXI logic
* matrix-level FSM
* buffer control
* packet handling

# 24. Do not over-pipeline unnecessarily

```text

accumulate
```

Document the resulting latency and modify the systolic schedule accordingly.

Never assume that inserting a register has no effect on data alignment.

## MOST IMPORTANT RULE

**Correctness is more important than completeness.**

If you discover that an earlier module or architectural decision is wrong, **stop, explain the problem, correct it, and propagate the correction through the dependent modules**.

Do not preserve an incorrect design merely because code has already been generated.

The final codebase must be internally consistent as a complete hardware system—not merely a collection of individually plausible SystemVerilog files.
